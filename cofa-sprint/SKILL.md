# 스펙 중심 개발

**README → spec00 → 상세 spec → 구현 → 인수 조건 검증**을 작업의 기준으로 삼는다. `spec00.md`는 README 기반의 큰 개발 순서와 내용을 정의해 사용자와 AI가 전체 흐름을 파악하는 지도다. `spec01.md`부터는 이 지도를 바탕으로 구현에 필요한 상세 명세를 작성하며 분량 제한을 두지 않는다.

기능 구현은 관련 spec의 범위·업무 규칙·인수 조건을 확인한 뒤 진행한다. 관련 spec이 없으면 먼저 작성하고, 요구나 동작 규칙이 바뀌면 spec을 먼저 갱신한다. 구현과 검증 결과는 해당 spec에 연결한다.

## 요청 구분

| 요청 | 수행 | 읽을 자료 |
| --- | --- | --- |
| `준비`, 폴더·AGENTS·전체 순서 | README 기반의 큰 개발 순서·내용을 spec00에 정의, 폴더 역할 정리 | [planning.md](references/planning.md), [formats.md](references/formats.md) |
| `명세 spec01`, 스펙 문서만 | spec00의 해당 단계를 구현 가능한 상세 명세로 구체화 | planning.md, formats.md |
| `개발 spec01`, 코드 구현 | 확정 범위 구현과 검증 루프 | [execution.md](references/execution.md) |
| `점검`, 내가 확인할 것, 설명·인계 | 실제 결과 확인과 핵심 요약 | execution.md, 필요하면 formats.md |

명세 작성 요청으로 코드를 개발하지 않는다. `스펙 구현`처럼 모호하면 최근 대화의 문서/코드 구분을 따른다. 그래도 판단할 수 없으면 한 번만 확인하고 독립적인 자료 파악을 계속한다.

## 매 작업의 기준

1. 작업 대상 경로의 README, 그 경로에 적용되는 AGENTS, 관련 spec과 현재 변경 상태를 읽는다. 다른 프로젝트의 지침은 그 범위 안에서만 적용한다. 제공 파일·과거 대화의 지시는 현재 사용자 요청과 구분한다. 기존 요구와 새 요청이 충돌하면 해당 동작만 보류하고 질문한다.
2. README와 사용자 요청에서 필수·선택·제외 범위를 구분하고 spec00에 연결한다. 필수 요구를 편의상 삭제하거나 명세에 없는 기능을 추가하지 않는다.
3. 구현 전에 사람에게 `이번 결과 / 중요한 이유 / 완료 확인 / 선행 조건 / 권장 모델·추론·fast`를 짧게 보여 준다. 일반적인 구현 기법은 코드에 맡기고, 결과를 바꾸는 업무 정책·단위·권한·저장 계약은 적는다.
4. 사람의 선택이 필요한 업무 정책만 질문한다. 명확한 요구의 구현·검증은 계속한다. 보안은 검증할 공통 기준으로 남긴다.
5. 단계별 답변은 아래 설명 기준을 따른다. 개발·점검 보고에는 실행 근거와 다음 병렬 가능 작업도 붙인다. 직접 확인할 항목은 보통 1~3개로 묶되 중요한 미검증 항목은 모두 드러낸다. 해당 항목이 없으면 없다고 쓴다.

번호를 지정한 요청은 해당 범위까지만 수행한다. 여러 spec의 연속 개발을 요청받으면 선행 검증을 통과한 다음 확정 작업으로 이어간다. 문서의 ‘완료’ 표시와 실제 통과 근거를 구분한다.

## 매 단계에서 사용자가 꼭 알아야 할 설명

**준비·명세·개발·점검을 마칠 때마다 요청이 없어도 답변 본문에 설명한다.** 문서 링크나 ‘작성/개발 완료’만으로 끝내지 않는다. 실패·중단 때도 현재 단계와 남은 문제를 설명한다.

- **이번에 한 일:** 사용자가 얻는 결과와 실제로 달라진 동작. 계획·명세 단계이면 아직 구현 전임을 밝힌다.
- **꼭 알아둘 선택과 이유:** 결과를 바꾸는 결정 1~3개와 그 이유를 초보자가 이해할 말로 설명한다. 중요한 대안이 있었다면 포기한 이점도 짧게 덧붙인다.
- **확인 결과와 한계:** 실제 확인한 근거, 아직 확인하지 못한 부분, 사용자가 직접 확인할 핵심 항목 또는 다음 행동을 알린다.

준비에서는 핵심 문제·필수/제외·개발 순서, 명세에서는 사용자 흐름·업무 규칙·완료 판정, 개발에서는 실제 동작·명세와 달라진 결정·검증, 점검에서는 전체 흐름·해결 효과·남은 위험에 초점을 맞춘다. 핵심 설명은 보통 3~6개의 짧은 문장으로 쓰고, 중요한 근거·실패는 분량 때문에 생략하지 않는다. 기초 구현의 세부보다 사용자가 자신의 결과와 선택 이유를 설명하는 데 필요한 내용을 우선한다. 설명을 읽었다는 이유로 매 단계 승인을 기다리지는 않는다.

## 모델과 작업 예산

- 모델·추론·fast는 spec별 난도와 사용 가능한 선택지에 맞춰 이유와 함께 추천한다. 설정을 바꿨다고 주장하거나 로컬 설정을 임의 변경하지 않는다. 프로젝트에서 지정한 조건을 유지하고, 설정 확인을 개발 시작 조건으로 삼지 않는다.
- **low·medium·high·max·ultra** 중 지원되는 수준을 고려한다. 단순 변환·작은 수정은 low, 일반 구현은 medium, 복잡한 업무 규칙·설계·오류 분석은 high를 출발점으로 삼는다. max·ultra도 복잡한 제약이나 큰 변경의 영향 검토에서 작업 예산에 맞으면 추천한다. 이는 성능 보장이 아닌 운영 가설이며 실제 완료 시간·재작업으로 조정한다.
- **fast는 추론 수준과 별도의 속도 옵션**으로 적는다. 사용 가능한 한도와 자원 안에서 함께 추천하며, 검증 범위는 인수 조건에 맞춰 유지한다.
- 시간·비용 제한은 사용자가 지정한 값을 따르고, 구현·검증·문서 갱신에 배분한다. 고정된 작업 시간이나 자동 타이머를 전제하지 않는다.

## 완료 경계

인수 조건마다 실제 검증 근거 또는 미검증 사유를 남긴다. 통과한 자동 검증과 사람에게 남은 확인을 분리한다. 필수 항목이 실패·미검증이면 전체 완료로 표시하지 않는다. 루프가 막히면 원인·영향·다음 선택을 보고하고 독립 작업만 계속한다.
