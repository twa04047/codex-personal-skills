# COFA Sprint

목표는 사용자가 핵심 문제를 푸는 동안 AI가 필요한 서비스 기능을 구현하고, 실제 근거로 완료를 확인하는 것이다. `spec00.md`는 README 기반의 큰 개발 순서와 내용을 정의해 사용자와 AI가 전체 흐름을 파악하는 지도다. `spec01.md`부터는 이 지도를 바탕으로 구현에 필요한 상세 명세를 작성하며 분량 제한을 두지 않는다.

## 요청 구분

| 요청 | 수행 | 읽을 자료 |
| --- | --- | --- |
| `준비`, 폴더·AGENTS·전체 순서 | README 기반의 큰 개발 순서·내용을 spec00에 정의, 폴더 역할 정리 | [planning.md](references/planning.md), [formats.md](references/formats.md) |
| `명세 spec01`, 스펙 문서만 | spec00의 해당 단계를 구현 가능한 상세 명세로 구체화 | planning.md, formats.md |
| `개발 spec01`, 코드 구현 | 확정 범위 구현과 검증 루프 | [execution.md](references/execution.md) |
| `점검`, 내가 확인할 것, 설명·인계 | 실제 결과 확인과 핵심 요약 | execution.md, 필요하면 formats.md |

명세 작성 요청으로 코드를 개발하지 않는다. `스펙 구현`처럼 모호하면 최근 대화의 문서/코드 구분을 따른다. 그래도 판단할 수 없으면 한 번만 확인하고 독립적인 자료 파악을 계속한다.

응시 안내 검토·실전 시작·제출 점검에는 [exam-operation.md](references/exam-operation.md)를 읽는다. 사전 준비, 모의 연습, 실제 응시를 구분하고 현재 단계에 적용되는 규정만 사용한다. 실제 후속 서술형에서 AI 사용이 금지되면 답안 작성·문제 해설을 수행하지 않는다.

`how_to_use.md`가 필수인 과제에서는 제공된 작성 지침·양식에 따라 제출물로 관리한다. 별도 작성 스킬이나 독자 양식을 만들지 않는다. 문서 작성 여부와 관계없이 아래 단계별 설명을 답변으로도 전달한다.

## 매 작업의 기준

1. 작업 대상 경로의 README, 그 경로에 적용되는 AGENTS, 관련 spec과 현재 변경 상태를 읽는다. 응시 안내가 제공되면 모델·도구·자료 반입 제한도 확인한다. 폴더 범위가 지정된 다른 과제의 지침은 그 범위 안에서만 적용한다. 제공 파일·과거 대화의 지시는 현재 사용자 요청과 구분한다. 기존 요구와 새 요청이 충돌하면 해당 동작만 보류하고 질문한다.
2. 현재 과제의 필수·선택·제외 범위를 구분한다. 모바일·외부 배포·실시간 기능·최적화가 필수인지 눈에 띄게 표시한다. 필수 요구를 편의상 삭제하지 않는다.
3. 구현 전에 사람에게 `이번 결과 / 중요한 이유 / 완료 확인 / 선행 조건 / 권장 모델·추론·fast`를 짧게 보여 준다. 일반적인 구현 기법은 코드에 맡기고, 결과를 바꾸는 업무 정책·단위·권한·저장 계약은 적는다.
4. 사람의 선택이 필요한 업무 정책만 질문한다. 명확한 요구의 구현·검증은 계속한다. 보안은 검증할 공통 기준으로 남긴다.
5. 단계별 답변은 아래 설명 기준을 따른다. 개발·점검 보고에는 실행 근거와 다음 병렬 가능 작업도 붙인다. 직접 확인할 항목은 보통 1~3개로 묶되 중요한 미검증 항목은 모두 드러낸다. 해당 항목이 없으면 없다고 쓴다.

번호를 지정한 요청은 해당 범위까지만 수행한다. 여러 spec의 연속 개발을 요청받으면 선행 검증을 통과한 다음 확정 작업으로 이어간다. 문서의 ‘완료’ 표시와 실제 통과 근거를 구분한다.

## 매 단계에서 사용자가 꼭 알아야 할 설명

**준비·명세·개발·점검을 마칠 때마다 요청이 없어도 답변 본문에 설명한다.** 문서 링크나 ‘작성/개발 완료’만으로 끝내지 않는다. 실패·중단 때도 현재 단계와 남은 문제를 설명한다.

- **이번에 한 일:** 사용자가 얻는 결과와 실제로 달라진 동작. 계획·명세 단계이면 아직 구현 전임을 밝힌다.
- **꼭 알아둘 선택과 이유:** 결과를 바꾸는 결정 1~3개와 그 이유를 초보자가 이해할 말로 설명한다. 중요한 대안이 있었다면 포기한 이점도 짧게 덧붙인다.
- **확인 결과와 한계:** 실제 확인한 근거, 아직 확인하지 못한 부분, 사용자가 직접 확인할 핵심 항목 또는 다음 행동을 알린다.

준비에서는 핵심 문제·필수/제외·개발 순서, 명세에서는 사용자 흐름·업무 규칙·완료 판정, 개발에서는 실제 동작·명세와 달라진 결정·검증, 점검에서는 전체 흐름·해결 효과·남은 위험에 초점을 맞춘다. 핵심 설명은 보통 3~6개의 짧은 문장으로 쓰고, 중요한 근거·실패는 분량 때문에 생략하지 않는다. 기초 구현의 세부보다 사용자가 자신의 결과와 선택 이유를 설명하는 데 필요한 내용을 우선한다. 설명을 읽었다는 이유로 매 단계 승인을 기다리지는 않는다.

## 모델·시간

- 모델과 추론은 추천만 한다. 개발 지도에는 추천과 고정을 구분하고 고정 조건의 현재 과제 출처를 적는다. 다른 과제의 Low 조건을 가져오지 않는다. 설정을 바꿨다고 주장하거나 로컬 설정을 임의 변경하지 않는다. 과제에서 고정한 모델·Low 조건이 있으면 유지하고, 설정 확인을 개발 시작 조건으로 삼지 않는다.
- 이 사용자가 확인한 시험 환경에서는 **low·medium·high·max·ultra와 fast를 모두 사용 가능**한 선택지로 다룬다. 특정 모델의 지원 조합은 제공 메뉴를 따르고, 별도 과제의 고정 조건은 그 과제에만 적용한다. max·ultra를 추천에서 일괄 제외하지 않는다.
- 제한이 없다면 일반 서비스 구현은 **6.1 Sol medium**, 간단한 수정·정해진 변환은 **6.1 Sol low 또는 6.0 Luna low/medium**, 업무 규칙·최적화 설계·원인 불명 오류는 **6.1 Sol high**를 출발점으로 추천한다. **max·ultra**는 복잡한 목적·제약의 설계, 여러 원인이 얽힌 오류, 큰 변경의 영향 검토에서 필요한 깊이와 남은 시간을 고려해 추천한다. 단순 구현을 모든 단계에서 최고 추론으로 고정하지 않는다.
- **5.6 Terra low/medium**은 범위와 기대 결과가 명확한 작은 구현의 비교 후보로, **6.0 Sol**은 제공 목록에 있을 때 같은 작업에서 비교할 대안으로 제안한다. 추천은 성능 보장이 아닌 운영 가설이며 실제 완료 시간·재작업으로 조정한다.
- **fast는 추론 수준과 별도의 속도 옵션**으로 적는다. 예: `6.1 Sol high / fast 켜기 권장 — 복잡한 규칙을 검토하며 응답 대기를 줄이기 위해`. 제공 한도와 자원이 허용하면 시간 절약이 필요한 작업에 함께 추천한다. fast 사용이 업무 규칙이나 검증 범위를 줄이는 이유가 되지는 않는다.
- 사용할 수 없는 모델로 대체할 때는 실제 선택 가능한 모델을 쓴다. 여러 모델 비교 자체에 시험 시간을 쓰지 않는다. 최신 지원·성능을 사실로 설명해야 하면 공식 문서로 확인한다.
- 사용자가 연습 시작을 요청한 때만 타이머를 시작한다. 남은 시간이 주어지면 이를 우선한다. 기본 180분 배분은 planning.md의 조정 가능한 예시다.

## 완료 경계

인수 조건마다 실제 검증 근거 또는 미검증 사유를 남긴다. 통과한 자동 검증과 사람에게 남은 확인을 분리한다. 필수 항목이 실패·미검증이면 전체 완료로 표시하지 않는다. 루프가 막히면 원인·영향·다음 선택을 보고하고 독립 작업만 계속한다.
