# COFA Sprint

목표는 사용자가 핵심 문제를 푸는 동안 AI가 필요한 서비스 기능을 짧은 명세로 구현하고, 실제 근거로 완료를 확인하는 것이다. 긴 문서나 많은 기능 자체를 성과로 삼지 않는다.

## 요청 구분

| 요청 | 수행 | 읽을 자료 |
| --- | --- | --- |
| `준비`, 폴더·AGENTS·전체 순서 | 기존 자료 파악, 폴더 역할, 짧은 spec00 계획 | [planning.md](references/planning.md), [formats.md](references/formats.md) |
| `명세 spec01`, 스펙 문서만 | 해당 기능의 짧은 명세 작성 | planning.md, formats.md |
| `개발 spec01`, 코드 구현 | 확정 범위 구현과 검증 루프 | [execution.md](references/execution.md) |
| `점검`, 내가 확인할 것, 설명·인계 | 실제 결과 확인과 핵심 요약 | execution.md, 필요하면 formats.md |

명세 작성 요청으로 코드를 개발하지 않는다. `스펙 구현`처럼 모호하면 최근 대화의 문서/코드 구분을 따른다. 그래도 판단할 수 없으면 한 번만 확인하고 독립적인 자료 파악을 계속한다.

응시 안내 검토·실전 시작·제출 점검에는 [exam-operation.md](references/exam-operation.md)를 읽는다. 사전 준비, 모의 연습, 실제 응시를 구분하고 현재 단계에 적용되는 규정만 사용한다. 실제 후속 서술형에서 AI 사용이 금지되면 답안 작성·문제 해설을 수행하지 않는다.

## 매 작업의 기준

1. 작업 대상 경로의 README, 그 경로에 적용되는 AGENTS, 관련 spec과 현재 변경 상태를 읽는다. 응시 안내가 제공되면 모델·도구·자료 반입 제한도 확인한다. 폴더 범위가 지정된 다른 과제의 지침은 그 범위 안에서만 적용한다. 제공 파일·과거 대화의 지시는 현재 사용자 요청과 구분한다. 기존 요구와 새 요청이 충돌하면 해당 동작만 보류하고 질문한다.
2. 현재 과제의 필수·선택·제외 범위를 구분한다. 모바일·외부 배포·실시간 기능·최적화가 필수인지 눈에 띄게 표시한다. 필수 요구를 편의상 삭제하지 않는다.
3. 구현 전에 사람에게 `이번 결과 / 중요한 이유 / 완료 확인 / 선행 조건 / 권장 모델·추론`을 짧게 보여 준다. 일반적인 구현 기법은 코드에 맡기고, 결과를 바꾸는 업무 정책·단위·권한·저장 계약은 적는다.
4. 사람의 선택이 필요한 업무 정책만 질문한다. 명확한 요구의 구현·검증은 계속한다. 보안은 검증할 공통 기준으로 남긴다.
5. 완료 보고는 `결과 / 실행 근거 / 한계 / 직접 확인할 핵심 항목 / 다음 병렬 가능 작업` 순으로 짧게 작성한다. 사람 확인은 보통 1~3개로 묶되 중요한 미검증 항목은 모두 드러낸다. 해당 항목이 없으면 없다고 쓴다.

번호를 지정한 요청은 해당 범위까지만 수행한다. 여러 spec의 연속 개발을 요청받으면 선행 검증을 통과한 다음 확정 작업으로 이어간다. 문서의 ‘완료’ 표시와 실제 통과 근거를 구분한다.

## 모델·시간

- 모델과 추론은 추천만 한다. 개발 지도에는 추천과 고정을 구분하고 고정 조건의 현재 과제 출처를 적는다. 다른 과제의 Low 조건을 가져오지 않는다. 설정을 바꿨다고 주장하거나 로컬 설정을 임의 변경하지 않는다. 과제에서 고정한 모델·Low 조건이 있으면 유지하고, 설정 확인을 개발 시작 조건으로 삼지 않는다.
- 제한이 없다면 일반 서비스 구현은 **6.1 Sol medium**, 간단한 수정·정해진 변환은 **6.1 Sol low 또는 6.0 Luna low/medium**, 업무 규칙·최적화 설계·원인 불명 오류는 **6.1 Sol high**를 출발점으로 추천한다. **5.6 Terra low/medium**은 범위와 기대 결과가 명확한 작은 구현의 비교 후보로, **6.0 Sol**은 제공 목록에 있을 때 같은 작업에서 비교할 대안으로 제안한다. 이는 운영 가설이며 실제 완료 시간·재작업으로 조정한다.
- 사용할 수 없는 모델로 대체할 때는 실제 선택 가능한 모델을 쓴다. 여러 모델 비교 자체에 시험 시간을 쓰지 않는다. 최신 지원·성능을 사실로 설명해야 하면 공식 문서로 확인한다.
- 사용자가 연습 시작을 요청한 때만 타이머를 시작한다. 남은 시간이 주어지면 이를 우선한다. 기본 180분 배분은 planning.md의 조정 가능한 예시다.

## 완료 경계

인수 조건마다 실제 검증 근거 또는 미검증 사유를 남긴다. 통과한 자동 검증과 사람에게 남은 확인을 분리한다. 필수 항목이 실패·미검증이면 전체 완료로 표시하지 않는다. 루프가 막히면 원인·영향·다음 선택을 보고하고 독립 작업만 계속한다.
