# 구현·검증·설명

## 시작 조건

명세 개발 요청이면 관련 spec과 인수 조건을 먼저 확인한다. 미정 업무 정책 또는 요구 충돌만 해당 부분의 차단 조건이다. 구현 기법은 합리적으로 선택한다. 선행 spec의 파일 존재나 ‘완료’ 문구만 믿지 말고, 의존하는 계약과 실행 증거를 확인한다.

DB를 바꾸면 기존 버전에서의 이전·데이터 보존과 새 DB 생성을 모두 검증한다. 사용자 실제 DB는 별도 권한이 없으면 변경하지 않고 임시 DB로 확인한다. 실행 환경·의존성 명령은 저장소에서 찾으며 고정된 pytest 개수나 패키지 경로를 추측하지 않는다.

## 작고 끝나는 검증 루프

1. 인수 조건에서 기대 결과를 정한다. 핵심 값은 원본·과제·작은 손계산에서 가져온다. 코드와 같은 가정을 복사한 테스트만으로 정확하다고 판단하지 않는다.
2. 최소 구현 후 관련 테스트·실제 API·필요한 브라우저 흐름을 실행한다. 명령, 대상 조건, 기대·관측 결과를 짧게 기록한다.
3. 실패하면 제품 오류/환경 오류를 구분하고 원인에 맞는 최소 수정을 한다. 실패한 조건과 영향받는 회귀를 다시 실행한다.
4. 관련 조건이 통과하면 해당 루프를 끝낸다. 새 변경·실패·미해결 우려가 없으면 같은 전체 검증을 반복하지 않는다.

기본은 **최초 검증 후 수정·재검증 최대 2회 또는 수정 루프 5분 중 먼저 도달하는 한도**다. 사용자가 지정한 예산이 우선한다. 첫 구현·최초 검증 시간을 이 한도와 혼동하지 않는다. 같은 실패가 두 번 반복되면 한도 전에라도 가정·선행 계약을 다시 확인한다. 막히면 실패 조건, 관측 증거, 시도한 수정, 후속 영향, 다음 제안을 보고한다. 더 긴 작업은 필요 시간과 범위를 설명하고 사용자의 남은 예산·지시 안에서 진행한다.

인수 조건을 느슨하게 바꾸거나 실패 테스트를 삭제해 통과시키지 않는다. 실제 관측한 실패가 없으면 실패·수정 사례를 꾸미지 않고 `첫 실행 통과`로 기록한다. 독립 작업은 실패한 선행 결과를 사용하지 않는 범위에서 계속한다.

## 검증을 적절히 나누기

- **기능마다:** 관련 정상 사례 + 중요한 경계/실패 + 공통 보호 기준 중 영향을 받는 조건.
- **선행 계약 변경 때:** 데이터 단위·건수·대표 결과, DB 새 설치·이전·보존, 소비 API 연결.
- **병렬 결과 통합 때:** 실제 데이터·인증을 거쳐 화면까지 연결한다. 각 창의 통과를 합친 것만으로 통합 통과라고 하지 않는다.
- **제출 전:** 모든 필수 요구의 누락 대조, 전체 핵심 흐름, 요구된 재시작·Docker·제출물 검사를 한 번 수행한다.

DOM 검사·HTTP 검사·실제 브라우저 조작을 구분한다. 브라우저 도구가 연결되지 않으면 구체적인 미검증 흐름을 알리고 사람이 할 클릭과 기대 결과를 준다. 환경 문제로 검증이 막힌 것을 기능 통과로 바꾸지 않는다. 재시도는 위 한도 안에서 수행한다.

자동화 방법은 해당 과제의 도구 제한을 따른다. Computer Use가 금지된 시험에서는 명령 기반 테스트·API 검증으로 루프를 운영하고 화면 조작은 사용자 확인으로 남긴다. 개별 브라우저 자동화 도구의 허용 여부가 명시되지 않았다면 허용을 가정하지 말고 제공 안내에서 확인한다.

## 증거와 상태

기존 검증 문서가 있으면 갱신한다. 없으면 `docs/verification.md` 한곳에 아래 표를 둔다. 긴 원시 로그·개인정보는 복사하지 않는다.

| 인수 조건 | 실행·입력 | 기대 → 관측 | 결과·미검증 |
| --- | --- | --- | --- |
| AC1 | 실제 명령/대표 입력 | 확인한 값 | 통과/실패/미검증과 이유 |

상태는 `초안 → 확정 → 구현 중 → 자동 검증 통과 → 인수 완료`를 필요한 만큼 쓴다. 사람 확인이 남으면 `자동 검증 통과·사용자 확인 대기`라고 적는다. 필수 자동 검증이 남아도 범위를 명시한다. 과거 테스트 수를 현재 실행 결과로 재사용하지 않는다.

## 사람이 직접 볼 지점

매 spec마다 승인을 기다리지 않는다. 다음 지점에 짧고 구체적인 확인을 모은다.

1. **초기 결정:** 필수·제외 범위, 핵심 목적·제약, 데이터 제외/수정 정책과 DB 계약 중 후속 결과를 바꾸는 부분.
2. **첫 핵심 결과:** 원본의 대표 한 건과 화면·분석 결과 대조, 중요한 권한 경계. AI가 확인한 것과 미검증인 것을 말한다.
3. **제출 전:** 실제 사용자 흐름, 해결안의 효과와 한계, 새 환경 실행·제출물에서 남은 중요한 확인.

항목은 `어디서 → 무엇을 → 어떤 결과면 정상인지`로 쓴다. 사람에게 반복 자동 테스트 실행을 떠넘기지 않는다. 사용자 확인이 필수라고 정한 결과는 기다리되, 독립된 작업은 계속한다.

## 서술형 대비와 인계

각 기능의 중요한 결정만 `docs/decisions.md` 또는 기존 설계 문서에 기록한다: **문제 → 선택 → 고려한 대안과 이유 → 실제 확인 → 한계**. 짧은 표나 몇 문장으로 충분하다. 해시 구현을 외우게 하기보다 왜 접근 제한이 필요한지와 어떻게 확인했는지 설명한다. 기술·리스크 질문이 오면 해당 코드와 검증 근거로 자세히 답한다.

연습·제출 전 설명 준비에서 사용자가 원하면 방금 구현한 내용에서 2~3개 질문을 내고 사용자의 말로 답하게 한다. 실제 응시의 후속 서술형은 시험 안내의 AI 금지 조건을 따른다. AI가 만든 모범답안을 사용자 이해의 증거로 기록하지 않는다.

다른 창에 인계할 때는 현재 계약·완료 증거·남은 실패·공유 파일 소유자·다음 실행을 한곳에 짧게 남긴다. 평가 기록은 실제 작업과 일치시킨다. 특정 스킬·루프 사용이 점수를 보장한다고 설명하지 않는다.
