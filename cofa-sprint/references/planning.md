# 범위를 줄이는 계획

## 준비

README의 요구를 `R1, R2…`로 묶어 spec00의 한 표에 연결한다. 이미 쓰는 번호·문서가 있으면 재사용한다. 기존 완료 스펙을 요청 없이 재작성하지 않는다.

첫 화면에 다음을 보여 준다.

- **핵심 문제:** 무엇을 개선하며 어떤 지표로 판단하는가.
- **필수 서비스:** 그 문제를 입력·조회·설명·제출하는 데 필요한 기능과 명시 요구.
- **제외 범위:** 모바일, 외부 배포, 실시간, 시각적 꾸밈 등 이번에 하지 않을 큰 항목. README가 요구하면 필수로 옮긴다.
- **중요 미정:** 결과가 달라지는 업무 정책만 질문한다. 예: 도보 한도, 버스 정원, 우선할 목적, 오류 자료 처리.

현업 담당자와 대화할 수 있으면 현재 업무·불편·목표·제약·판정 기준을 묻고 답을 명세에 반영한다. 기초 용어·질문 가능한 영역부터 확인해도 된다. 현업 담당자에게 정답과 해결 순서를 통째로 요구하는 것과, 맥락을 정한 뒤 코딩 에이전트에 작업 분해를 맡기는 것을 구분한다.

폴더는 필요한 `spec/`, `src/`, `docs/`, `tests/`만 준비한다. 원본 위치는 기존 구조를 따른다. 폴더별 AGENTS가 요청되면 formats.md의 짧은 역할 지침을 적용한다. 기존 AGENTS와 spec 양식은 보존하며 변경 요청이 있을 때만 중복 없이 갱신한다. 기존 양식이 더 상세하면 이를 따르고, 단순화 변경을 현재 요청이 허용하는지 확인한다.

## spec00은 작업 설명서가 아니라 지도

표 열: `spec / 사용자 결과 / 요구 ID / 선행 spec·계약 / 담당 파일 / 완료 확인 / 모델·추론·fast / 상태`.

기능을 너무 작은 설치·함수 단위로 쪼개지 말고 **사용자가 한 가지 일을 끝낼 수 있는 단위**로 묶는다. 보통 몇 개의 기능 묶음이면 충분하다. 10단계나 90개 작업을 목표로 정하지 않는다. 큰 spec 안의 내부 개발 순서는 AI가 관리한다.

각 필수 요구는 한 spec 또는 공통 검증에 연결한다. 제외·후순위 기능도 명시하여 빠짐과 의도적 제외를 구분한다. 필수 기능을 후순위로 미뤄도 미완료임을 유지한다.

## 개별 spec은 짧은 계약

formats.md를 사용해 대략 한 화면에서 읽을 수 있는 분량을 목표로 쓴다. 다음 내용은 빠뜨리지 않는다.

- 사용자가 얻는 결과, 포함·제외, 요구 근거.
- 결과를 바꾸는 입력·출력·업무 규칙. 정상·핵심 경계·권한/실패를 관찰 가능한 인수 조건으로 쓴다.
- 중요한 선택 **1~3개에만 이유**를 붙인다. 코드 한 줄·일반 구현 방식마다 이유를 반복하지 않는다.
- 선행 계약·담당 파일·검증 방법·직접 확인할 핵심 결과.

공유되지 않는 파일명, 모든 DB 열, 완전한 API JSON, 라이브러리 사용법은 필요할 때만 상세화한다. **다른 창이 의존하는 ID·필드·단위·상태·API 요청/응답과 오류는 정확히 적는다.** DB 이전, 손실 가능 처리, 최적화 제약은 짧게 쓰려고 생략하지 않는다. 긴 계약은 해당 spec의 부록 한곳에 두고 참조한다.

## 공통 보호 기준

spec00에 한 번만 기록하고 관련 spec은 참조한다. 기술을 외우는 부담은 줄이고, AI가 실행으로 책임지게 한다.

| 대상 | 검증할 결과 |
| --- | --- |
| 계정·권한이 있으면 | 안전한 비밀번호 해시, 로그인·로그아웃/만료, 미로그인·타인·관리자 접근 경계, 비활성 처리 |
| 웹 입력·저장이 있으면 | 매개변수화 쿼리, 출력 이스케이프, 입력 검증, 쿠키 세션의 변경 요청 CSRF 방어·적절한 쿠키 설정 |
| 비밀·개인정보가 있으면 | 필요한 필드만 반환, 로그·오류·제출물에 비밀/불필요 개인정보 제외 |
| 영속 저장·데이터 반영이 있으면 | 단위·중복·참조 검증, 재실행 보존, 실패 취소, 필요한 DB 이전, 재시작 후 보존 |

기존 프레임워크의 표준 기능을 우선하고 보안 기능을 직접 새로 설계하지 않는다. 이 기준의 통과는 전체 보안 감사나 모든 취약점 부재를 의미하지 않는다.

## 의존성과 병렬 작업

의존성이 없는 번호라는 이유만으로 병렬 실행하지 않는다. **동작 계약과 쓰는 파일**을 함께 확인한다.

1. 공통 데이터 의미·DB 버전/이전·인증·API 계약을 한 담당자가 정한다.
2. 두 작업이 서로의 미완료 결과를 사용하지 않고 수정 파일도 분리되면 병렬 후보로 표시한다.
3. 공통 DB, 앱 등록, 의존성 파일, 공통 CSS·상태 문서는 통합 담당자 한 명이 소유한다. 구현자는 필요한 변경을 인계한다.
4. 각 창에 `담당 파일 / 읽을 계약 / 선행 통과 증거 / 인수 조건 / 금지된 공통 변경 / 검증 명령 / 인계 위치`를 준다. 다른 작업자의 변경을 되돌리지 않도록 알린다.
5. 선행 계약만 정해졌다면 소비자는 가짜 데이터로 준비할 수 있다. **실제 선행 결과의 검증과 연결 검증 전에는 통합 완료로 표시하지 않는다.** 계약이 바뀌면 소비자를 멈추고 영향 범위를 갱신한다.

처음에는 구현 창 2개 정도로 시작해 통합 비용을 관찰한다. 모델의 추론을 낮추거나 창을 늘리는 것 자체가 충돌 방지책은 아니다. 별도 체크아웃·worktree는 환경과 요청에 맞게 선택하며 사용자의 기존 변경을 보존한다.

제공 환경의 RAM·CPU를 확인해 무거운 서버·빌드·테스트가 겹치지 않게 배치한다. 자원이 부족하면 작업 수를 줄이고 완료한 프로세스를 정리한다. 병렬 수를 늘리기 위해 시험 환경이나 감독·운영 프로세스를 바꾸지 않는다. 사용 가능한 native 하위 에이전트나 터미널 분할을 활용하고 추가 오케스트레이션 도구를 필수로 설치하지 않는다.

## 문제풀이 시간을 먼저 확보

최적화가 실제 과제에 포함되면 웹 기능보다 목적·제약·기준안·검산에 시간을 배정한다. 현재 과제가 조회 서비스뿐이면 최적화를 새 요구로 넣지 않는다.

180분의 예시: **0~15분** 범위·데이터·공통 계약, **15~105분** AI의 최소 서비스와 사용자의 핵심 분석을 병행, **105~145분** 결과 연결·검산·대표 흐름, **145~180분** 새 기능 중단·전체 검증·제출·설명. 계약 이후 사용자는 분석에 60~90분을 확보하도록 조정한다. 시간 부족은 필수 요구 삭제 사유가 되지 않으며 남은 실패를 공개한다.

정류장 최적화 예시라면 최대 도보거리·정원·근무 시각을 먼저 확정하고, 현재 배치 같은 기준안과 후보를 비교한다. 도보 한도를 고정한 뒤 미탑승 인원을 최소화하고 다음으로 버스 수를 줄이는 방식 등 **목적의 우선순위를 사용자와 정한다.** 탑승 인원·버스 수·도보 거리·제약 위반을 독립 계산으로 검산하고, 한도나 정원을 바꾼 경우를 비교한다. 휴리스틱이면 전역 최적해라고 주장하지 않는다.
